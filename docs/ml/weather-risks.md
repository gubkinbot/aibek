## 1. Цель и контекст

### Бизнес-проблема

Газотранспортная система Узбекистана работает в условиях **экстремального континентального климата**: от −25°C зимой до +50°C летом. Погодные явления напрямую влияют на надёжность инфраструктуры:

| Погодное явление | Влияние на ГТС |
|-----------------|----------------|
| Сильные морозы (< −15°C) | Замерзание конденсата, обледенение оборудования, хрупкость металла |
| Аномальная жара (> +45°C) | Перегрев компрессоров, снижение КПД ГПА, деформация надземных участков |
| Пыльные/песчаные бури | Засорение фильтров, абразивный износ, снижение видимости |
| Сильный ветер (> 25 м/с) | Повреждение надземных конструкций, линий электропередач |
| Сели и паводки | Размыв грунта над подземными трубопроводами, затопление объектов |
| Землетрясения | Деформация трубопроводов, разгерметизация |
| Резкие перепады температуры | Термическое напряжение в трубах, усталость сварных швов |

Сейчас реакция на погоду — **реактивная**: диспетчеры узнают о проблемах от персонала на местах. Нет системы раннего предупреждения, привязанной к конкретным объектам инфраструктуры.

### ML-задача

**Multi-source risk scoring** — объединение прогноза погоды, географии объектов и характеристик инфраструктуры в единую оценку риска:

| Подзадача | Тип | Описание |
|-----------|-----|----------|
| Оценка риска для объекта | Risk scoring (regression) | Числовой скор 0–100 для каждого объекта ГТС |
| Классификация уровня угрозы | Multi-class classification | Зелёный / Жёлтый / Оранжевый / Красный |
| Раннее предупреждение | Alerting | Автоматическое формирование штормового предупреждения |

### Заказчик

Диспетчерский центр, Служба эксплуатации линейной части, Служба ОТ и ТБ.

### Метрики успеха

| Метрика | Описание | Целевое значение |
|---------|----------|-----------------|
| Охват инцидентов | % инцидентов, которым предшествовал повышенный risk score | ≥ 80% |
| Время предупреждения | Среднее время от алерта до реализации риска | ≥ 24 часа |
| False alarm rate | Доля красных алертов без последующего инцидента | ≤ 15% |
| Покрытие территории | % объектов ГТС, покрытых мониторингом | 100% |

## 3. Базелайн

### Текущий процесс

| Метод | Описание | Проблема |
|-------|----------|----------|
| Штормовое предупреждение Узгидромет | Общие предупреждения по регионам | Не привязано к объектам ГТС; нет оценки severity |
| Опыт диспетчера | «В Бухаре ожидается мороз — проверьте КС-7» | Субъективно; не масштабируется; зависит от человека |
| Регламент | Усиленный режим при T < −15°C | Порог одинаковый для всех объектов; не учитывает другие факторы |

### Базелайн для ML

| Метод | Описание | Ожидаемый охват инцидентов |
|-------|----------|---------------------------|
| Rule-based | Фиксированные правила: T < −15 → красный для всех КС | ~50% (не учитывает комбинации) |
| Weighted rules | Правила с весами: мороз + старое оборудование + высокая нагрузка → красный | ~65% |
| Logistic regression | Простая модель на метео + характеристиках объекта | ~70% |

## 4. Модель

### Подход

Двухуровневая система:

```
Уровень 1: Risk Score для каждого объекта
  Входы: [метео_прогноз, характеристики_объекта, история_инцидентов, нагрузка]
  Выход: score 0–100
      ↓
Уровень 2: Агрегация и алертинг
  score → Зелёный (0–25) / Жёлтый (25–50) / Оранжевый (50–75) / Красный (75–100)
      ↓
Карта рисков + список объектов по приоритету
```

### Кандидаты моделей

| Модель | Обоснование |
|--------|-------------|
| **Gradient Boosting (XGBoost/LightGBM)** | Основной кандидат: хорошо работает с табличными данными, обрабатывает пропуски, interpretable через SHAP |
| **Random Forest** | Robust, менее склонен к переобучению; хорош как baseline |
| **Neural Network (MLP)** | Если хватит данных об инцидентах; может уловить нелинейные взаимодействия |
| **Rule-based + ML hybrid** | Экспертные правила как features для ML модели |

### Интерпретируемость

::: warning Критически важно
Для системы раннего предупреждения **недостаточно** просто показать «красный». Оператор должен понимать **почему**:
- «Риск высокий из-за: прогноз −22°C + возраст оборудования 18 лет + подводный переход»
:::

Решение: **SHAP values** для каждого предсказания:

```
Объект: КС-7 (Бухара)
Risk Score: 82 / 100 (Красный)

Почему:
  Температура −22°C (прогноз)     ████████████  +35
  Возраст оборудования (18 лет)   ████████      +22
  Ветер 18 м/с                    ████          +12
  Последний инцидент 3 мес назад  ███           +8
  Базовый риск                    ██            +5
```

## 5. Оценка

### Офлайн-метрики

| Метрика | Описание | Целевое |
|---------|----------|---------|
| **Recall (красный)** | % реальных инцидентов, для которых модель давала «красный» | ≥ 85% |
| **Precision (красный)** | % красных алертов, за которыми последовал инцидент | ≥ 50% |
| **AUC-ROC** | Общее качество ранжирования рисков | ≥ 0.85 |
| **Brier Score** | Калибровка вероятностей | ≤ 0.15 |
| **Lead time** | Среднее время между алертом и инцидентом | ≥ 24 часа |

::: info Баланс precision/recall
Для системы безопасности **recall важнее**. Лучше 10 ложных жёлтых алертов, чем 1 пропущенный красный. Но false alarm rate не должен превышать 15%, иначе система потеряет доверие.
:::

### Валидация

- **Temporal split**: обучение на 3+ годах, тест на последнем году
- **Leave-one-station-out**: проверка обобщаемости на новый объект
- **Stress-test**: оценка на исторических экстремальных событиях (морозы 2022, жара 2023 и т.д.)

## 6. Деплой

### Режим работы

| Компонент | Частота |
|-----------|---------|
| Загрузка метео-прогноза | Каждые 3 часа |
| Расчёт risk scores | Каждые 3 часа (после обновления метео) |
| Обновление карты рисков | Real-time (по мере пересчёта) |
| Переобучение модели | Ежемесячно / после каждого инцидента |

### Пайплайн

```
Каждые 3 часа:
  ↓
Метео API → прогноз на 72ч по координатам всех объектов
  ↓
Feature engineering (метео × объект × история)
  ↓
Inference (XGBoost → risk score 0–100 для каждого объекта)
  ↓
SHAP values (объяснение для каждого скора)
  ↓
Сохранение в TimescaleDB
  ↓
API: GET /api/ml/weather-risks?region=bukhara&level=red
  ↓
Дашборд: карта Узбекистана с цветовой индикацией
  ↓
Алерты: Оранжевый → email; Красный → email + Telegram + SMS
```

### Дашборд (целевой)

- **Карта Узбекистана** с объектами ГТС, окрашенными по уровню риска
- **Список «горячих» объектов** — топ-10 по risk score с объяснением (SHAP)
- **Временная шкала** — прогноз рисков на 72 часа вперёд
- **История** — как менялся risk score объекта за последнюю неделю
- **Метео-оверлей** — температура, ветер, осадки на карте

## 7. Риски

### Технические

| Риск | Вероятность | Влияние | Митигация |
|------|------------|---------|-----------|
| Мало данных об инцидентах для обучения | Высокая | Высокое | Data augmentation; экспертная разметка; синтетические сценарии |
| Неточный прогноз погоды | Средняя | Среднее | Ансамбль метео-источников; калибровка uncertainty |
| Неполный реестр объектов ГТС | Средняя | Среднее | Постепенное дополнение; начать с критических объектов |
| Модель не обобщается на редкие события | Средняя | Высокое | Rule-based fallback для экстремальных значений |

### Бизнесовые

| Риск | Митигация |
|------|-----------|
| «Слишком много жёлтых алертов» — усталость | Настраиваемые пороги по ролям; фильтр по зоне ответственности |
| Юридическая ответственность за пропуск | Система — **advisory tool**, финальное решение за человеком |
| Зависимость от внешнего метео API | Кэширование на 24ч; собственные метеопосты как fallback |
