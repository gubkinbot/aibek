# Проект 1: Предиктивная аналитика компрессорных станций

::: info Статус
**Фаза:** Проектирование | **Приоритет:** Высокий | **Начало:** TBD

## 1. Цель и контекст

### Бизнес-проблема

Компрессорные станции (КС) — критическая инфраструктура газотранспортной системы АО «Узтрансгаз». Они поддерживают давление в магистральных газопроводах для транспортировки газа на большие расстояния. Внеплановый простой одной КС может привести к:

- Снижению пропускной способности газопровода
- Нарушению поставок потребителям
- Дорогостоящему аварийному ремонту
- Рискам для безопасности персонала

Сейчас обслуживание выполняется по регламенту (планово-предупредительное) или по факту отказа (реактивное). Оба подхода неоптимальны: плановое обслуживание не учитывает реальное состояние оборудования, а реактивное — слишком дорого и опасно.

### ML-задача

**Предиктивная аналитика** — переход от «ремонт по расписанию» к «ремонт по состоянию»:

| Подзадача | Тип | Описание |
|-----------|-----|----------|
| Обнаружение аномалий | Anomaly Detection | Раннее выявление отклонений в работе оборудования |
| Прогноз остаточного ресурса | Regression (RUL) | Оценка оставшегося времени до отказа |
| Классификация состояния | Multi-class Classification | Определение текущего состояния: норма / внимание / критическое |

### Заказчик

Управление транспортировки газа, Диспетчерский центр.

### Метрики успеха

| Метрика | Описание | Целевое значение |
|---------|----------|-----------------|
| Снижение внеплановых простоев | % уменьшения неплановых остановок КС | ≥ 30% за первый год |
| Предупреждение за N часов | Среднее время от алерта до реального отказа | ≥ 48 часов |
| False alarm rate | Доля ложных срабатываний | ≤ 5% |
| Adoption rate | % операторов, использующих систему | ≥ 80% |

## 2. Данные

### Источники

| Источник | Тип данных | Частота | Формат |
|----------|-----------|---------|--------|
| SCADA / АСУ ТП | Телеметрия оборудования | 1–60 сек | Числовые ряды |
| Система техобслуживания | Журналы ремонтов, замен | По факту | Структурированные записи |
| Оперативный журнал | Записи операторов | Посменно | Текст |
| Паспорта оборудования | Характеристики, наработка | Статические | Документы |

### Ключевые сигналы (features)

**Газотурбинные агрегаты (ГПА):**
- Температура: масла, подшипников, выхлопных газов, воздуха на входе
- Давление: масла, газа на входе/выходе, перепад на фильтрах
- Вибрация: подшипников компрессора и турбины (осевая, вертикальная, горизонтальная)
- Обороты: ротора компрессора и турбины (RPM)
- Расход: газа через компрессор, топливного газа

**Вспомогательные системы:**
- Система маслоснабжения: уровень, температура, давление масла
- Система охлаждения: температура хладагента на входе/выходе
- Электрооборудование: ток, напряжение, мощность

### Объём данных (оценка)

| Параметр | Значение |
|----------|---------|
| Количество КС | 10–20 станций |
| Сенсоров на КС | 50–200 |
| Частота опроса | 1–60 секунд |
| Глубина истории | 2–5 лет (цель) |
| Объём в день | ~50–200 MB на станцию |

### Качество данных — известные проблемы

- **Пропуски** — обрывы связи со SCADA, плановые остановки
- **Шум** — помехи в аналоговых сигналах вибрации
- **Неразмеченные отказы** — исторические инциденты не всегда задокументированы
- **Разнородность** — разные КС имеют разное оборудование и наборы сенсоров

### Пайплайн данных (целевой)

```
SCADA / OPC UA
    ↓
Коннектор (опрос сенсоров)
    ↓
Буфер (Redis / Kafka)
    ↓
ETL (валидация, интерполяция пропусков, нормализация)
    ↓
TimescaleDB (hypertable, партиционирование по времени)
    ↓
Feature Store (агрегаты: скользящие средние, тренды, дельты)
```

## 3. Базелайн

### Как задача решается сейчас

| Метод | Описание | Проблема |
|-------|----------|----------|
| Планово-предупредительный ремонт (ППР) | Обслуживание по расписанию (наработка в часах) | Не учитывает реальное состояние; избыточное или недостаточное обслуживание |
| Пороговые алерты | SCADA генерирует алерт при превышении уставки | Реагирует слишком поздно; много ложных срабатываний |
| Экспертная оценка | Опытные операторы «чувствуют» проблемы | Субъективно; зависит от конкретного человека; не масштабируется |

### Базелайн для ML-модели

Для корректной оценки ML-модели нужен числовой базелайн:

| Базелайн | Метод | Ожидаемая точность |
|----------|-------|-------------------|
| Naive threshold | Фиксированные пороги по каждому сенсору (текущие уставки SCADA) | Recall ~60%, Precision ~40% |
| Statistical Z-score | Z-score по скользящему окну, алерт при > 3σ | Recall ~70%, Precision ~55% |
| Isolation Forest (unsupervised) | Простая модель без разметки | Recall ~75%, Precision ~65% |

ML-модель должна **превзойти лучший базелайн** и по recall, и по precision.

## 4. Модель

### Подход

Многоуровневая система:

```
Уровень 1: Обнаружение аномалий (unsupervised)
  ↓ Аномалия обнаружена
Уровень 2: Классификация состояния (supervised)
  ↓ Состояние «Внимание» или «Критическое»
Уровень 3: Прогноз RUL (regression)
  → «Ожидаемый отказ через N часов»
```

### Кандидаты моделей

| Уровень | Метод | Обоснование |
|---------|-------|-------------|
| Аномалии | Autoencoder (LSTM) | Хорошо улавливает временные паттерны; не требует разметки аномалий |
| Аномалии | Isolation Forest | Простой, быстрый; хорош как первая итерация |
| Классификация | Gradient Boosting (XGBoost/LightGBM) | Эффективен на табличных фичах (агрегаты сенсоров) |
| Классификация | 1D-CNN | Работает на сырых временных рядах, улавливает локальные паттерны |
| RUL | LSTM / GRU | Стандарт для прогноза остаточного ресурса |
| RUL | Transformer (temporal) | Лучше улавливает долгосрочные зависимости |

### Feature Engineering

| Группа фичей | Примеры |
|--------------|---------|
| Мгновенные | Текущие значения всех сенсоров |
| Статистические | Mean, std, min, max за окно (1ч, 6ч, 24ч, 7д) |
| Трендовые | Линейный тренд за окно, скорость изменения |
| Межсенсорные | Корреляции между парами сенсоров, дельта вход-выход |
| Контекстные | Режим работы (нагрузка %), наработка от последнего ТО |

### Фреймворк

| Компонент | Технология |
|-----------|-----------|
| Обработка данных | pandas, polars |
| Feature engineering | tsfresh (автоматическая генерация фичей из временных рядов) |
| Классические модели | scikit-learn, XGBoost, LightGBM |
| Нейросети | PyTorch |
| Experiment tracking | MLflow (или custom на TimescaleDB) |

## 5. Оценка

### Офлайн-метрики

| Метрика | Описание | Целевое |
|---------|----------|---------|
| **Precision** | Доля реальных аномалий среди предсказанных | ≥ 85% |
| **Recall** | Доля обнаруженных аномалий из всех реальных | ≥ 90% |
| **F1-score** | Гармоническое среднее P и R | ≥ 87% |
| **Time-to-detection** | Время от начала аномалии до её обнаружения | ≤ 2 часа |
| **RUL MAE** | Средняя абсолютная ошибка прогноза RUL | ≤ 12 часов |

::: warning Приоритет
**Recall важнее Precision.** Пропущенный отказ стоит значительно дороже ложного алерта. Но false alarm rate > 10% приведёт к «алертной усталости» операторов.
:::

### Онлайн-метрики

| Метрика | Как измеряется |
|---------|---------------|
| Кол-во предотвращённых инцидентов | Подтверждённые алерты, по которым приняты меры до отказа |
| Время реакции | Среднее время от алерта до действия оператора |
| Feedback rate | % алертов, на которые оператор дал обратную связь (верно/ложно) |

### Критерий перехода в production

1. F1 ≥ 87% на тестовой выборке (hold-out, последние 3 месяца)
2. False alarm rate ≤ 5% за 30 дней shadow mode
3. Не менее 2 подтверждённых верных предсказаний в shadow mode
4. Положительный отзыв от 3+ операторов КС

## 6. Деплой

### Режим работы

| Компонент | Режим | Частота |
|-----------|-------|---------|
| Сбор данных | Real-time | Каждые 1–60 сек |
| Обнаружение аномалий | Near real-time | Каждые 5 минут |
| Классификация состояния | Near real-time | При обнаружении аномалии |
| Прогноз RUL | Batch | Каждый час (для оборудования в статусе «Внимание») |
| Переобучение | Batch | Еженедельно / по требованию |

### Инфраструктура

```
TimescaleDB (данные) → Feature Pipeline (Python) → Model Serving (FastAPI)
                                                          ↓
                                                    Predictions DB
                                                          ↓
                                                    Vue 3 Dashboard
                                                          ↓
                                                    Алерты (email, Telegram)
```

### Мониторинг модели

| Что мониторим | Как | Порог |
|---------------|-----|-------|
| Data drift | PSI (Population Stability Index) по входным фичам | PSI > 0.2 → алерт |
| Prediction drift | Распределение скоров аномалий | Kolmogorov-Smirnov p < 0.01 |
| Точность | Сравнение предсказаний с реальными инцидентами | F1 < 0.8 → переобучение |
| Латентность | Время inference | p95 > 10 сек → оптимизация |

### Откат

При деградации модели:
1. Автоматический возврат к предыдущей версии
2. Fallback на пороговые алерты (базелайн)
3. Уведомление ML-команде

## 7. Риски

### Технические

| Риск | Вероятность | Влияние | Митигация |
|------|------------|---------|-----------|
| Нехватка размеченных данных об отказах | Высокая | Высокое | Начать с unsupervised (аномалии); активная разметка с операторами |
| Разное оборудование на разных КС | Высокая | Среднее | Transfer learning; отдельные модели по типам ГПА |
| Обрывы связи со SCADA | Средняя | Среднее | Буферизация на КС; модель устойчива к пропускам (imputation) |
| Concept drift (изменение условий) | Средняя | Высокое | Мониторинг дрифта; регулярное переобучение |

### Бизнесовые

| Риск | Митигация |
|------|-----------|
| Недоверие операторов к системе | Shadow mode → постепенный ввод; UX с объяснениями причин алерта |
| Алертная усталость | Строгий контроль false alarm rate; приоритизация алертов |
| Зависимость от качества SCADA | Параллельно работать над качеством данных в SCADA |

### Этические

- Система **помогает** операторам, но **не заменяет** их решения
- Финальное решение о действиях всегда за человеком
- Не используется для оценки эффективности персонала

## 8. Команда и ресурсы

### Роли

| Роль | Обязанности |
|------|------------|
| ML Engineer | Модели, пайплайны, деплой |
| Data Engineer | ETL, подключение SCADA, качество данных |
| Domain Expert (инженер КС) | Разметка данных, валидация результатов, экспертиза |
| Frontend Developer | Дашборд мониторинга, UX алертов |
| Product Owner | Приоритеты, координация с бизнесом |

### Инфраструктура

| Ресурс | Назначение | Требования |
|--------|-----------|-----------|
| GPU-сервер | Обучение нейросетей | 1× NVIDIA A100/V100 или RTX 4090 |
| CPU-сервер | Inference, пайплайны | 16+ cores, 64 GB RAM |
| TimescaleDB | Хранение временных рядов | SSD, retention policy |

### Timeline (ориентировочный)

| Фаза | Длительность | Результат |
|------|-------------|-----------|
| Discovery | 4–6 недель | Доступ к данным, EDA, понимание домена |
| Базелайн + первая модель | 6–8 недель | Работающий прототип (anomaly detection) |
| Улучшение + RUL | 6–8 недель | Полная система (аномалии + классификация + RUL) |
| Shadow mode | 4–8 недель | Валидация на реальных данных без влияния на процессы |
| Production | 2–4 недели | Полноценная работа с алертами |
