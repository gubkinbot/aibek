# Проект 2: Прогнозирование потребления газа

::: info Статус
**Фаза:** Проектирование | **Приоритет:** Высокий | **Начало:** TBD

## 1. Цель и контекст

### Бизнес-проблема

АО «Узтрансгаз» управляет газотранспортной системой (ГТС) Узбекистана — сетью магистральных газопроводов, компрессорных станций и газораспределительных узлов. Для стабильной работы ГТС необходимо **заранее знать**, сколько газа потребуют все участники системы.

Дисбаланс приводит к:
- **Дефицит** — падение давления в трубе, отключение потребителей, аварийные режимы
- **Избыток** — повышение давления, увеличение нагрузки на КС, лишние энергозатраты
- **Финансовые потери** — штрафы по контрактам, закупка/продажа газа на спотовом рынке

Сейчас балансировка выполняется вручную диспетчерами на основе опыта и сезонных коэффициентов. Точность прогноза низкая, особенно при резких изменениях погоды.

### ML-задача

**Прогнозирование временных рядов** (Time Series Forecasting):

| Горизонт | Применение | Требуемая точность |
|----------|-----------|-------------------|
| **Краткосрочный** (1–3 дня) | Оперативная балансировка ГТС | MAPE ≤ 5% |
| **Среднесрочный** (1–4 недели) | Планирование режимов КС, закупки | MAPE ≤ 10% |
| **Долгосрочный** (1–12 месяцев) | Бюджетирование, инвестиционное планирование | MAPE ≤ 15% |

### Заказчик

Центральный диспетчерский центр, Управление балансировки газа.

### Метрики успеха

| Метрика | Описание | Целевое значение |
|---------|----------|-----------------|
| MAPE (краткосрочный) | Средняя % ошибка прогноза на 1–3 дня | ≤ 5% |
| MAPE (среднесрочный) | Средняя % ошибка прогноза на неделю | ≤ 10% |
| Покрытие пиков | % пиковых дней, предсказанных с точностью ±10% | ≥ 85% |
| Время подготовки прогноза | От запроса до готового результата | ≤ 30 минут |

## 2. Данные

### Источники

| Источник | Тип данных | Частота | Описание |
|----------|-----------|---------|----------|
| Коммерческий учёт газа | Объёмы потребления | Суточный / часовой | Факт по потребителям и группам |
| Метеоданные | Температура, ветер, осадки | Почасовой | Факт и прогноз по регионам |
| Календарь | Рабочие дни, праздники | — | Узбекистан: гос. праздники, Рамадан, Навруз |
| Экономические показатели | Промышленное производство | Месячный | Индексы промпроизводства по отраслям |
| Данные ГТС | Давление, расход в узлах | Часовой | SCADA/телемеханика |

### Сегментация потребителей

| Сегмент | Описание | Доля | Особенности |
|---------|----------|------|------------|
| Население | Бытовое потребление | ~30% | Сильная зависимость от температуры (отопление) |
| Промышленность | Заводы, фабрики | ~35% | Стабильнее; зависит от графика работы |
| Энергетика | ТЭС, ТЭЦ | ~25% | Зависит от электропотребления, которое тоже сезонно |
| Экспорт | Контрактные обязательства | ~10% | Планируется заранее |

### Ключевые features

| Группа | Примеры |
|--------|---------|
| Временные | Час, день недели, месяц, квартал, день года |
| Календарные | Рабочий/выходной, праздник, Рамадан |
| Метео | Температура (факт и прогноз), ветер, облачность |
| Лаговые | Потребление вчера, неделю назад, месяц назад, год назад |
| Скользящие | Среднее потребление за 7/14/30 дней, тренд |
| Экзогенные | Цена газа (если есть), промышленный индекс |
| Географические | Регион потребления (Ташкент, Бухара, Фергана и т.д.) |

## 3. Базелайн

### Текущие методы

| Метод | Описание | MAPE (оценка) |
|-------|----------|---------------|
| Прошлый год + коэффициент | Потребление аналогичного периода прошлого года × 1.02–1.05 | 15–25% |
| Экспертная оценка диспетчера | Корректировка на основе опыта и погоды | 10–20% |
| Сезонные нормативы | Плановые лимиты по месяцам из бюджета | 20–30% |

### Базелайн для ML

| Модель | Описание | Ожидаемый MAPE |
|--------|----------|---------------|
| Seasonal Naive | Значение того же дня прошлой недели | 12–18% |
| SARIMA | Классическая статистическая модель с сезонностью | 8–14% |
| Prophet (Meta) | Автоматическая декомпозиция: тренд + сезонность + праздники | 7–12% |

## 4. Модель

### Подход

Ансамбль из нескольких моделей с последующим стекингом:

```
Данные (features)
    ↓
┌───────────────┬─────────────────┬──────────────────┐
│  LightGBM     │  Prophet        │  LSTM / N-BEATS  │
│  (таблица)    │  (декомпозиция) │  (нейросеть)     │
└───────┬───────┴────────┬────────┴─────────┬────────┘
        │                │                  │
        ▼                ▼                  ▼
┌───────────────────────────────────────────────────┐
│              Stacking (Ridge / Linear)             │
│              Финальный прогноз                     │
└───────────────────────────────────────────────────┘
```

### Кандидаты моделей

| Модель | Тип | Плюсы | Минусы |
|--------|-----|-------|--------|
| **LightGBM** | Gradient boosting | Быстрый; хорошо работает с табличными фичами (лаги, календарь, метео) | Не улавливает сложные временные зависимости |
| **Prophet** | Additive decomposition | Автоматическая сезонность; легко добавить праздники Узбекистана | Слабо учитывает экзогенные факторы |
| **N-BEATS** | Deep learning (univariate) | SOTA для univariate forecasting; interpretable version | Требует много данных; не использует экзогенные |
| **Temporal Fusion Transformer** | Deep learning (multivariate) | Учитывает все типы фичей; attention для интерпретируемости | Сложная настройка; долгое обучение |
| **LSTM** | RNN | Классика для временных рядов | Vanishing gradient; уступает современным архитектурам |

### Рекомендация: начать с LightGBM + Prophet

**Почему:** быстрая итерация, понятные результаты, не требуют GPU. Нейросети — второй этап.

### Гранулярность моделей

| Вариант | Описание | Когда использовать |
|---------|----------|--------------------|
| Одна модель на всю систему | Суммарный прогноз потребления | Быстрый старт |
| Модель на сегмент | Население, промышленность, энергетика отдельно | Основной режим |
| Модель на регион | По областям Узбекистана | При достаточных данных |
| Иерархическая reconciliation | Сумма частных = общий (hierarchical forecasting) | Продвинутый уровень |

## 5. Оценка

### Офлайн-метрики

| Метрика | Формула | Описание |
|---------|---------|----------|
| **MAPE** | mean(|actual - pred| / actual) × 100% | Основная метрика; % ошибка |
| **MAE** | mean(|actual - pred|) | Абсолютная ошибка (в м³/сут) |
| **RMSE** | sqrt(mean((actual - pred)²)) | Штрафует за большие ошибки |
| **Bias** | mean(pred - actual) | Систематическое завышение/занижение |
| **Peak MAPE** | MAPE только для дней с потреблением > P90 | Точность в пиковые дни |

### Стратегия валидации

```
Train                    │  Val    │  Test
─────────────────────────┤─────────┤──────────
    3+ лет истории       │ 3 мес   │ 3 мес
                         │         │ (самые свежие)

+ Expanding window cross-validation:
  [Train 1 year] → [Val 1 month]
  [Train 1y+1m]  → [Val next month]
  ...
```

::: warning Важно
**Нельзя** делать random split для временных рядов — только time-based split. Иначе модель будет «подглядывать» в будущее.
:::

### Критерий перехода в production

1. MAPE ≤ 5% для краткосрочного прогноза (3 мес. тестовых данных)
2. MAPE ≤ 10% для среднесрочного прогноза
3. Bias < ±2% (модель не должна систематически завышать/занижать)
4. Peak MAPE ≤ 10% (пиковые дни прогнозируются корректно)
5. 2 недели shadow mode с параллельным сравнением с экспертным прогнозом

## 6. Деплой

### Режим работы

| Прогноз | Обновление | Когда запускается |
|---------|-----------|-------------------|
| Краткосрочный (1–3 дня) | Ежедневно в 06:00 | После получения факта за предыдущие сутки |
| Среднесрочный (1–4 нед) | Еженедельно (ПН) | После получения недельного факта |
| Долгосрочный (1–12 мес) | Ежемесячно | После закрытия месяца |

### Пайплайн

```
06:00  Cron job
  ↓
Загрузка факта за вчера (коммерческий учёт)
  ↓
Загрузка прогноза погоды (метео API)
  ↓
Feature engineering (лаги, скользящие, календарь)
  ↓
Inference (LightGBM + Prophet → stacking)
  ↓
Сохранение в TimescaleDB (таблица predictions)
  ↓
API endpoint: GET /api/ml/gas-forecast?horizon=3d
  ↓
Дашборд: график прогноза vs факта
  ↓
Алерт, если прогноз > порог (аномальное потребление)
```

### Дашборд (целевой)

- График: прогноз vs факт (линейная диаграмма с доверительным интервалом)
- Таблица: прогноз по сегментам / регионам на завтра
- Карта: теплокарта потребления по областям Узбекистана
- Метрики: текущий MAPE за последние 7/30/90 дней

### Мониторинг

| Метрика | Порог | Действие |
|---------|-------|----------|
| MAPE за 7 дней | > 8% | Алерт ML-команде |
| MAPE за 30 дней | > 6% | Переобучение модели |
| Пропуск факта | Нет данных за вчера до 06:00 | Использовать прогноз метео + лаг; алерт |
| Аномальный прогноз | Отклонение > 3σ от нормы | Пометить как suspicious; алерт диспетчеру |

## 7. Риски

### Технические

| Риск | Вероятность | Влияние | Митигация |
|------|------------|---------|-----------|
| Низкое качество данных коммерческого учёта | Высокая | Высокое | Валидация: outlier detection, проверка на пропуски; работа с поставщиками данных |
| Прогноз погоды неточен | Средняя | Среднее | Использовать ансамбль метео-провайдеров; учитывать uncertainty прогноза |
| Структурные изменения потребления | Средняя | Высокое | Мониторинг дрифта; быстрое переобучение; fallback на короткие лаги |
| Аномальные события (заморозки, газ. кризис) | Низкая | Высокое | Специальная обработка outliers; ручной override диспетчером |

### Бизнесовые

| Риск | Митигация |
|------|-----------|
| Диспетчеры не доверяют модели | Shadow mode; показывать рядом с экспертным прогнозом; постепенный переход |
| Неверный прогноз в пиковый день | Консервативный bias в зимний период; дополнительный запас |
| Зависимость от внешних API (метео) | Кэширование; fallback на собственные метеостанции |
