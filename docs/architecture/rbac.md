# Система ролей (RBAC)

Платформа использует гибкую систему управления доступом на основе ролей (Role-Based Access Control) с поддержкой групп и организационной структуры.

## Основные понятия

### Роли (Roles)

Роль — это именованный набор прав (permissions). Пользователь может иметь несколько ролей.

**Системные роли** (создаются автоматически, нельзя удалить/редактировать):

| Роль | Описание |
|------|----------|
| `superadmin` | Полный доступ. Автоматически проходит **все** проверки permissions. Нельзя заблокировать или удалить. |
| `admin` | Управление пользователями и настройками. По умолчанию имеет все permissions кроме `roles.manage`. |
| `user` | Базовый доступ. По умолчанию без дополнительных permissions. |

Можно создавать **пользовательские роли** (например, `operator`, `analyst`) с любым набором permissions.

### Разрешения (Permissions)

Permission — это конкретное действие в системе. Permissions назначаются ролям и группам, а не пользователям напрямую.

**Полный список permissions:**

| Codename | Описание | Категория |
|----------|----------|-----------|
| `users.view` | Просмотр пользователей | users |
| `users.create` | Создание пользователей | users |
| `users.edit` | Редактирование пользователей | users |
| `users.delete` | Удаление пользователей | users |
| `users.block` | Блокировка/разблокировка пользователей | users |
| `users.reset_password` | Сброс пароля пользователей | users |
| `roles.view` | Просмотр ролей | roles |
| `roles.manage` | Создание, редактирование, удаление ролей | roles |
| `groups.view` | Просмотр групп | groups |
| `groups.manage` | Управление группами | groups |
| `departments.view` | Просмотр подразделений | departments |
| `departments.manage` | Управление подразделениями | departments |
| `audit.view` | Просмотр журнала действий | audit |

### Группы (Groups)

Группа — это набор пользователей с общими permissions. Удобно для предоставления одинаковых прав целому отделу или команде.

Пример: группа «Аналитики» с permissions `users.view` и `audit.view` — все участники автоматически получают эти права.

### Подразделения (Departments)

Подразделения — это организационная структура компании (дерево). Используются для отражения структуры организации.

Подразделения **не дают permissions** — это чисто организационная сущность. Пользователь может принадлежать нескольким подразделениям.

```
АО «Узтрансгаз»
├── Центральный аппарат
│   ├── IT-отдел
│   ├── Бухгалтерия
│   └── HR
├── Управление транспортировки газа
│   ├── Диспетчерский центр
│   └── Техническое обслуживание
└── Региональные отделения
    ├── Ташкентское отделение
    └── Бухарское отделение
```

## Как проверяются права

Когда пользователь обращается к защищённому эндпоинту, проверка идёт так:

```
1. Пользователь — superadmin?
   → ДА: доступ разрешён (всегда)
   → НЕТ: продолжаем

2. У какой-нибудь роли пользователя есть нужный permission?
   → ДА: доступ разрешён
   → НЕТ: продолжаем

3. У какой-нибудь группы пользователя есть нужный permission?
   → ДА: доступ разрешён
   → НЕТ: 403 Forbidden
```

### Пример в коде

```python
# Эндпоинт, доступный пользователям с permission "users.view"
@router.get("/users")
async def list_users(
    current_user: User = Depends(require_permission("users.view")),
):
    ...
```

Функция `require_permission` — это фабрика FastAPI-зависимостей:
1. Проверяет JWT-токен
2. Загружает пользователя из БД
3. Проверяет, что пользователь активен (не заблокирован)
4. Проверяет наличие permission по иерархии (superadmin → роли → группы)

## Схема базы данных

```
┌─────────┐     ┌──────────────┐     ┌──────────┐
│  Users  │────→│  user_roles  │←────│  Roles   │
│         │     └──────────────┘     │          │
│         │                          │          │
│         │     ┌──────────────┐     │          │     ┌──────────────┐     ┌─────────────┐
│         │────→│ user_groups  │←────│  Groups  │────→│group_perms   │←────│ Permissions │
│         │     └──────────────┘     └──────────┘     └──────────────┘     │             │
│         │                                                                │             │
│         │     ┌──────────────┐     ┌────────────┐   ┌──────────────┐     │             │
│         │────→│ user_depts   │←────│Departments │   │ role_perms   │←────│             │
└─────────┘     └──────────────┘     │            │   └──────────────┘     └─────────────┘
                                     │  parent ↑  │
                                     │  children↓ │
                                     └────────────┘
```

**Связующие таблицы (many-to-many):**

| Таблица | Связь | Дополнительные поля |
|---------|-------|---------------------|
| `user_roles` | User ↔ Role | `assigned_at`, `assigned_by` (кто назначил) |
| `role_permissions` | Role ↔ Permission | — |
| `user_groups` | User ↔ Group | — |
| `group_permissions` | Group ↔ Permission | — |
| `user_departments` | User ↔ Department | — |

## Суперадминистратор

Суперадмин — особая роль с абсолютными правами:

- **Автоматически проходит все проверки** permissions (не нужно назначать конкретные rights)
- **Нельзя заблокировать** — попытка вернёт 403
- **Нельзя удалить** — попытка вернёт 403
- **Нельзя сбросить пароль** (может только другой superadmin)
- Только superadmin может **назначить роль superadmin** другому пользователю

### Как стать суперадмином

1. Укажите email в `.env`:
   ```env
   SUPERADMIN_EMAIL=admin@utg.uz
   ```
2. Зарегистрируйтесь с этим email
3. Подтвердите email кодом — роль `superadmin` назначится автоматически

Альтернативно: если пользователь уже зарегистрирован и верифицирован, роль назначится при следующем запуске бэкенда (в процессе инициализации).

## Аудит-лог

**Все** административные действия записываются в журнал аудита:

| Что записывается | Описание |
|-----------------|----------|
| `actor_id` | Кто выполнил действие |
| `action` | Тип действия (`user.block`, `role.create` и т.д.) |
| `target_type` | Тип объекта (`user`, `role`, `group`, `department`) |
| `target_id` | ID объекта |
| `details` | JSON с деталями (old/new значения) |
| `ip_address` | IP-адрес администратора |
| `created_at` | Когда выполнено |

Подробный список действий — в [API — Администрирование](../api/admin).

## Сценарии использования

### Сценарий 1: Новый сотрудник

1. Админ создаёт пользователя через admin-панель
2. Назначает роль `user`
3. Назначает в подразделение «IT-отдел»
4. Добавляет в группу «Аналитики» (если нужны доп. permissions)

### Сценарий 2: Повышение до администратора

1. Superadmin открывает карточку пользователя
2. Назначает роль `admin` (или создаёт кастомную роль с нужными permissions)
3. Действие записывается в аудит-лог

### Сценарий 3: Увольнение сотрудника

1. Админ блокирует пользователя с указанием причины
2. Пользователь больше не может войти
3. Данные сохраняются для аудита
