# Система контроля доступа

Платформа использует модульную систему контроля доступа на основе **уровней доступа к модулям** и флага **суперадминистратора**.

## Основные понятия

### Модули

Платформа разделена на функциональные модули. Каждый модуль — это самостоятельная область функциональности:

| Модуль | Описание |
|--------|----------|
| `admin` | Администрирование: пользователи, аудит, мониторинг |
| `compressor` | Компрессорные станции |
| `balance` | Балансировка ГТС |
| `weather` | Погодные риски |
| `digital` | Цифровой департамент |
| `ai_chat` | ИИ-чат |
| `scada` | SCADA — управление запорной арматурой |

### Уровни доступа

Каждый модуль поддерживает **4 уровня доступа**. Уровень определяет, какие действия пользователь может выполнять в модуле:

| Уровень | Описание | Permissions |
|---------|----------|-------------|
| `viewer` | Наблюдатель — только просмотр данных | `{module}.access`, `{module}.view` |
| `operator` | Оператор — просмотр и работа с данными | `{module}.access`, `{module}.view`, `{module}.edit` |
| `manager` | Руководитель — полное управление модулем | `{module}.access`, `{module}.view`, `{module}.edit`, `{module}.manage` |
| `admin` | Администратор — администрирование и настройки | `{module}.access`, `{module}.view`, `{module}.edit`, `{module}.manage`, `{module}.admin` |

Каждый следующий уровень **включает все permissions предыдущего**.

### Модуль `admin` — особый случай

Модуль `admin` имеет собственный набор permissions, отличающийся от проектных модулей:

| Уровень | Permissions |
|---------|-------------|
| `viewer` | `users.view`, `audit.view` |
| `operator` | `users.view`, `users.create`, `users.edit`, `users.delete`, `users.block`, `users.reset_password`, `audit.view` |
| `manager` | то же, что operator |
| `admin` | operator + `system.view`, `system.manage` |

### Суперадминистратор

Суперадминистратор — пользователь с флагом `is_superadmin = true`. Это **не уровень доступа**, а отдельный флаг:

- **Автоматически проходит все проверки** permissions — не нужно назначать уровни доступа
- **Нельзя заблокировать** — попытка вернёт 403
- **Нельзя удалить** — попытка вернёт 403
- **Нельзя сбросить пароль** (может только другой суперадминистратор)
- Только суперадминистратор может **назначить/снять флаг суперадмина** другому пользователю
- Не может изменить свой собственный статус суперадмина

## Как проверяются права

Когда пользователь обращается к защищённому эндпоинту, проверка идёт так:

```
1. Пользователь — суперадминистратор (is_superadmin)?
   → ДА: доступ разрешён (всегда)
   → НЕТ: продолжаем

2. Для каждой записи module_access пользователя:
   → Получаем набор permissions для пары (module, level)
   → Если нужный permission есть в наборе → доступ разрешён

3. Ни одна запись не содержит нужный permission?
   → 403 Forbidden
```

### Пример в коде

```python
# Эндпоинт, доступный пользователям с permission "users.view"
@router.get("/users")
async def list_users(
    current_user: User = Depends(require_permission("users.view")),
):
    ...
```

Функция `require_permission` — фабрика FastAPI-зависимостей:
1. Проверяет JWT-токен
2. Загружает пользователя из БД (с `module_access` через `selectin`)
3. Проверяет, что пользователь активен (не заблокирован)
4. Проверяет наличие permission: `is_superadmin` → уровни модулей

### Пример: как формируются permissions

Допустим, у пользователя:
- `module_access`: `compressor → operator`, `admin → viewer`
- `is_superadmin`: `false`

Его итоговые permissions:
```
compressor.access, compressor.view, compressor.edit  (от compressor:operator)
users.view, audit.view                                (от admin:viewer)
```

Этот пользователь может:
- Просматривать realtime данные, аварии и аномалии компрессорных станций (`compressor.view`)
- Квитировать аварии (`compressor.edit`)
- Просматривать список пользователей и журнал аудита

Но **не может**: управлять тегами и правилами (`compressor.manage`), администрировать станции (`compressor.admin`), видеть другие модули.

### Пример: permissions модуля «Компрессорные станции»

| Permission | Что даёт доступ |
|------------|----------------|
| `compressor.access` | Вход на страницу модуля (отображение в дашборде) |
| `compressor.view` | Просмотр станций, тегов, realtime, истории, аварий, аномалий |
| `compressor.edit` | Квитирование аварий и аномалий |
| `compressor.manage` | CRUD тегов, вычисляемых тегов, правил аварий и аномалий, импорт Excel, диагностика |
| `compressor.admin` | CRUD станций, генерация сертификатов, полное управление |

## Как назначается доступ

### Назначение уровней модулей

Администратор (с permission `users.edit`) назначает пользователю уровень доступа к модулю через админ-панель или API:

```http
PUT /api/admin/module-access/users/{user_id}
Content-Type: application/json

{
  "module": "compressor",
  "level": "operator"
}
```

Каждый пользователь может иметь **по одному уровню на каждый модуль**. При повторном назначении — уровень обновляется.

### Назначение суперадминистратора

**Автоматически при запуске:**

1. Укажите email в `.env`:
   ```env
   SUPERADMIN_EMAIL=admin@utg.uz
   ```
2. Зарегистрируйтесь с этим email и подтвердите его
3. При следующем запуске бэкенда флаг `is_superadmin` установится автоматически

**Вручную через API:**

```http
PUT /api/admin/users/{user_id}/superadmin
```

Только суперадминистратор может вызвать этот эндпоинт. Флаг переключается (toggle): если был `true` — станет `false`, и наоборот.

## Отображение на фронтенде

Каждая страница модуля показывает пользователю его уровень доступа:

- **Цветной бейдж** с названием уровня (Наблюдатель / Оператор / Руководитель / Администратор / Суперадминистратор)
- **Список возможностей** — что пользователь может делать на текущем уровне

Данные берутся из `auth.user.module_access` (ответ `/auth/me`).

| Уровень | Цвет бейджа |
|---------|-------------|
| Наблюдатель | Серый |
| Оператор | Синий |
| Руководитель | Фиолетовый |
| Администратор | Оранжевый |
| Суперадминистратор | Красный |

## Аудит-лог

**Все** административные действия записываются в журнал аудита:

| Что записывается | Описание |
|-----------------|----------|
| `actor_id` | Кто выполнил действие |
| `action` | Тип действия (`user.block`, `user.module_access.set` и т.д.) |
| `target_type` | Тип объекта (`user`) |
| `target_id` | ID объекта |
| `details` | JSON с деталями (old/new значения) |
| `ip_address` | IP-адрес администратора |
| `created_at` | Когда выполнено |

### Типы действий

| Действие | Описание |
|----------|----------|
| `user.create` | Создание пользователя |
| `user.edit` | Редактирование данных пользователя |
| `user.block` | Блокировка аккаунта |
| `user.unblock` | Разблокировка аккаунта |
| `user.delete` | Удаление пользователя |
| `user.reset_password` | Сброс пароля администратором |
| `user.superadmin.toggle` | Переключение флага суперадминистратора |
| `user.module_access.set` | Назначение/изменение уровня доступа к модулю |
| `user.module_access.remove` | Удаление доступа к модулю |

Подробный список эндпоинтов — в [API — Администрирование](../api/admin).

## Сценарии использования

### Сценарий 1: Новый сотрудник

1. Администратор создаёт пользователя через админ-панель
2. Назначает уровни доступа к нужным модулям (например, `compressor → operator`, `admin → viewer`)
3. Пользователь входит и видит доступные модули на дашборде

### Сценарий 2: Повышение прав

1. Администратор открывает карточку пользователя
2. Изменяет уровень доступа к модулю (например, `compressor → operator` → `compressor → manager`)
3. Действие записывается в аудит-лог с деталями: старый и новый уровень

### Сценарий 3: Увольнение сотрудника

1. Администратор блокирует пользователя с указанием причины
2. Пользователь больше не может войти
3. Все данные о доступе сохраняются для аудита

### Сценарий 4: Назначение нового суперадмина

1. Текущий суперадминистратор открывает карточку пользователя
2. Включает флаг «Суперадминистратор»
3. Новый суперадмин получает полный доступ без ограничений
